Domain Services

MemberOneClient Setup + Enrollment

Flow 1: Client Setup — POST /fhir/client

Infrastructure setup done once per TPA/employer before any member can enroll.

  • Creates: Organization (TPA/Payer/Employer/Network), OrganizationAffiliation, InsurancePlan
  • 4 event types: Partner Publish, Relationship Publish, Employer Publish, Plan Publish
  • Input: collection Bundle (NOT transaction/batch)
  • All-or-nothing atomic — failure rolls back everything
  • 8-step pipeline: UUID → Validate IG → Resolve IDs → POST vs PUT → Order → Refs → FHIR Proxy → Response Bundle

Flow 2: Enrollment — POST /fhir/member

  • Source: Flume platform (TPA enrollment files → FHIR)
  • Input: collection Bundle (Patient + Coverage)
  • 12-step pipeline including COB rules engine, InsurancePlan lookup, accumulator notification
  • InsurancePlan must exist before enrollment (Step 8 fatal if not found)
ClaimsClaims Adjudication

Primary Resource: ExplanationOfBenefit (EOB)

  • Lifecycle: draft → active → cancelled (immutable once active)
  • Never mutate active — cancel old + create new active
  • Each EOB carries stable identifier + created timestamp

Nected Rule Engine (6 rules in order)

  1. IsEligible (Coverage/Member lookup)
  2. GetTier (Provider API)
  3. DetermineBenefitOutcomeCode (Terminology/Reference API)
  4. Pricing (Pricing API)
  5. Accumulator (Accumulator API)
  6. Enrich

3 Integration Models

  • Coupe adjudicates end-to-end
  • Coupe adjudicates benefits, TPA owns accumulators
  • TPA adjudicates; Coupe ingests finalized claims for Member Portal

4. Playwright TypeScript Test Automation Framework

Framework Production-ready API + E2E + DB test framework

Tech Stack

  • Playwright ^1.47.0 + TypeScript 5.x (strict, ESM)
  • Node.js 20 LTS
  • Schema validation: AJV (JSON Schema)
  • Test data: @faker-js/faker, csv-parse
  • Accessibility: @axe-core/playwright
  • DB: AWS Athena (via AWS SDK — SQL over HealthLake views)

Reporters

Allure HTML Playwright HTML JUnit XML

CI/CD

GitHub Actions (4-shard) Azure DevOps GitLab CI

Framework Design Rules

  • Locators: getByRole > getByLabel > getByTestId — no raw CSS/XPath
  • No waitForTimeout() anywhere
  • No direct process.env in tests — all via config/env.ts
  • No assertions inside Page Objects
  • test.step() in every test for trace viewer
  • Tags: @smoke, @regression in test titles
  • Auth state freshness: 30-min TTL in global-setup
  • ignoreHTTPSErrors: true on Auth0 context (corporate proxy TLS)

Auth Strategy

  • Auth0 client_credentials OAuth2 flow
  • Token cached until 60s before expiry (helper: auth0Helper.ts)
  • Routes through HTTPS_PROXY (same as Postman configuration)

5. Employer Load Logic — Database Specification for Client Setup Tests

DB Spec Employer_Table_Load_Logic_v9.xlsx — Source of Test Cases

Defines how an employer setup Excel file flows through ODS staging → SQL Server stored procedures → BCBSMN_Trusted tables → FHIR resources in HealthLake. Every SP INSERT step maps 1:1 to a FHIR resource type the Client Setup POST creates internally.

11-Step New Employer SP Pipeline

StepTableKey Rule
1EmployerEmployerCode+SponsorID dup → skip
2EmployerPBMPBMTypeID must be 30019 or 30047
6PBMChoice★ PayerKey MUST be 3/140/143
7PlanPlanCode+EffDate dup → skip
10DivisionDate-expand only — no duplicate rows
11PlanDivisionLeaf-level eligibility resolution

Fatal Validations → Negative Test Cases

  • PayerKey not in (3=Aetna, 140=BCBS MN, 143=BCBS AL) → 422
  • PBMTypeID not 30019/30047 → 400
  • TPACode not in reference table → 400
  • Organization.name blank → 422
  • Renewal for non-existent employer → 404

ISNULL Defaults → Positive Test Cases

  • BadDebtMultiplier → 0.15 when omitted
  • OOPType → "Embedded"
  • TermDate → "9999-12-31" (open-ended)
  • Deductible/OOP amounts → 0.00

All 11 steps are wrapped in a single BEGIN TRANSACTION → ROLLBACK — any failure rolls back the entire employer row atomically.
